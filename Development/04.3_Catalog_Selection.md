        # 1. Sprint Goal

        The objective of Sprint 4.3 is to build a lightning-fast catalog selection interface.

        The user should be able to:
        1. Search services via text.
        2. Browse categories and popular items.
        3. Add services and products with a single tap.
        4. Adjust quantities directly in the list.
        5. Review selected items.
        6. Continue to the Billing Engine.

        **CRITICAL RULE:** No pricing or reward calculations occur in this sprint. The Catalog Selection module *only* prepares an array of selected items `{ id, quantity, price }` and passes them to the Billing Engine (Sprint 4.2).

        ---

## Included (MVP)

- OTP Verification

## Phase 2

- Favorites with data persistence

        ```text
                ↓
        (User can either Search OR Browse Categories)
                ↓

        ↓                             ↓
        ```

        - **Offline:** Shows offline banner, prevents selection if catalog not cached.
        - **No Catalog:** Shows Empty Catalog state with prompt to add manual items (or redirects to setup).
        - **Empty Search:** Shows "No results found" for the query.

- **Route:** `/(app)/visit` — **This is the single-page wizard. There is NO separate `/visit/catalog` route.** The visit flow is controlled by `useBillingStore.step`. When step = `'catalog'`, this view is rendered within the `/visit` page. See `07_Application_Architecture.md` Section 4.1.

        # 6. Database

        ## Tables Touched

        ### `catalogs`
        - **Reads:** Fetch active catalog for the `business_id`.
        - **Relationships:** `business_id` -> `businesses.id`.

        ### `categories`
        - **Reads:** Fetch categories linked to the business/catalog.
        - **Relationships:** `catalog_id` -> `catalogs.id`.

        ### `catalog_items`
        - **Reads:** Fetch active items, prices, and categories.
        - **Relationships:** `category_id` -> `categories.id`.
        - **Indexes:** `business_id + is_active`, `category_id`.

        ### `transactions` (Read Only - Future proofing)
        - **Reads:** Analyze past transactions to populate "Recently Used" or "Popular" items (optional for MVP, but architecturally supported).

        **Caching:**
        Catalog data changes infrequently during the day. Use TanStack Query with a high `staleTime` (e.g., 5-10 minutes) to ensure instantaneous loading.

        ---

        # 7. Server Actions

        ### `getCatalog()`
        - **Purpose:** Fetch the complete list of active categories and items for the business.
        - **Input:** `businessId` (derived from session).
        - **Validation:** User must be authenticated and own/staff the business.
        - **Output:** `{ categories: Category[], items: CatalogItem[] }`
        - **Errors:** `AUTH_REQUIRED`, `CATALOG_NOT_FOUND`, `SERVER_ERROR`.
        - **Caching:** `['catalog', businessId]`, Stale: 5m.

        ### `searchCatalog()`
        - **Purpose:** Server-side search if client-side filtering is insufficient. (For MVP, fetching the full catalog and filtering client-side is preferred if size < 1000 items).
        - **Input:** `query`
        - **Output:** `CatalogItem[]`

        ### `getCategories()`
        - **Purpose:** Fetch only categories (often combined with `getCatalog`).

        ### `getPopularItems()`
        - **Purpose:** Fetch top 10 items based on historical transaction volume.
        - **Input:** `businessId`
        - **Output:** `CatalogItem[]`

        ### `validateCatalog()`
        - **Purpose:** Pre-flight check before passing to Billing Engine to ensure selected items are still active and prices haven't changed maliciously.

        ---

        # 8. Validation

        - **Duplicate Items:** Prevented by Zustand store mapping (adding the same item increments quantity instead of adding a duplicate row).
        - **Quantity:** Must be an integer >= 1.
        - **Availability:** Items with `status = 'inactive'` are filtered out by `getCatalog()`. No stock tracking in MVP.
        - **Deleted/Inactive Items:** Filtered out in `getCatalog()`.
        - **Maximum Quantity:** Cap at 99 per item to prevent UI breakage and accidental massive bills.
        - **Minimum Quantity:** 1. Dropping below 1 removes the item.

        ---

        # 9. Search Behaviour

        - **Debounce:** 300ms delay on keystrokes before filtering.
        - **Search Ranking:** Exact matches first, partial matches second.
        - **Partial Match:** Matches anywhere in the item name.
        - **Category Filter:** If a category is selected, search applies *only* within that category, OR typing automatically switches to an "All" view to show global results (Preferred: Global search overrides category tabs).
        - **Recent Search:** Not required for MVP.
        - **Keyboard:** Standard text keyboard.
        - **Auto Focus:** No. Let user browse first.
        - **Paste:** Supported. Strips special characters if necessary.

        ---

        # 10. Quantity Rules

        - **Default quantity:** Tapping an item card for the first time sets quantity to 1.
        - **Increase:** Tapping '+' increments by 1.
        - **Decrease:** Tapping '-' decrements by 1.
        - **Maximum:** 99.
        - **Minimum:** 1.
        - **Remove:** Tapping '-' when quantity is 1 removes the item entirely.
        - **Undo Remove:** Toast notification with "Undo" action (optional UX enhancement).
        - **Long Press:** Not supported in MVP (keep it simple).
        - **Rapid Taps:** UI must not lag. Zustand store handles synchronous rapid updates.

        ---

        # 11. Selected Items Rules

        - **Sort Order:** Order in which they were added (chronological).
        - **Edit:** Can change quantities directly in the Selected Items view.
        - **Delete:** Can remove items directly.
        - **Quantity:** Summed up for the "Items" badge on the Continue button.
        - **Subtotal Preview:** The UI may display a basic `Item Price × Qty` sum for visual feedback, but **this is a preview only**.
        - **Continue Button:** Transitions the selected array to the Billing Engine.

        **Responsibilities:**
        - Catalog Selection builds the `CartItem[]` array.
        - Billing Calculations remain completely inside the Billing Engine (`04.2_Billing_Engine.md`).

        # 13. State Management

        ## TanStack Query
        - `['catalog', businessId]`: Fetches the entire active catalog and categories. Stale time: 5 minutes.
        - `['catalog', 'popular', businessId]`: Fetches frequently used items.

        ## Zustand (`useBillingStore`)
        - Reuses the store from Sprint 4.2.
        - Actions used: `addItem`, `updateQuantity`, `removeItem`.
        - State read: `items` (Array of selected catalog items).

        ## React Hook Form / Local State
        - `searchQuery` managed via local `useState` with debounce.
        - `activeCategory` managed via local `useState`.
        - `isSheetOpen` managed via local `useState`.

        # 18. Edge Cases

        - **Large Catalog (1000+ Items):** Client-side filtering may lag. Consider virtualized lists (`react-window` or similar) if performance drops.
        - **Duplicate Selection:** Handled by Zustand store. `addItem` checks if ID exists; if yes, calls `updateQuantity(+1)`.
        - **Deleted Item:** If an item is in the Zustand store but deleted from the DB between visits, `validateCatalog()` in Sprint 4.2 catches it.
        - **Offline:** Catalog loads from TanStack cache. Search and selection work offline if cached.
        - **Refresh:** Browser refresh clears Zustand store. User loses selected items (acceptable for MVP counter app).
        - **Back Navigation:** Preserves Zustand store. User can go back to Customer Selection, change customer, and return without losing items.
        - **Session Expired:** Handled globally by interceptors.
        - **Rapid Quantity Changes:** Local state debounces or Zustand handles synchronous state updates flawlessly.
        - **Keyboard Open:** Searching collapses categories. Sticky footer must remain visible above keyboard.

        # 30. Catalog Synchronization Strategy

        When the catalog changes while a user is creating a bill, the application must handle the following synchronization scenarios seamlessly:

        ### Item Price Updated
        Item selected
        ↓
        Price changes in database
        ↓
        Billing Engine reloads latest price
        ↓
        Show informational message
        ↓
        Recalculate bill

        ### Item Deleted
        Item selected
        ↓
        Item removed from catalog
        ↓
        Prevent checkout
        ↓
        Remove item
        ↓
        Notify user

        ### Item Deactivated
        Item becomes inactive
        ↓
        Cannot be selected
        ↓
        If already selected
        ↓
        Remove from selection
        ↓
        Notify user

        ### Category Updated
        Category renamed
        ↓
        Refresh categories
        ↓
        Maintain selected items

        ### Catalog Updated From Another Device
        Invalidate TanStack Query
        ↓
        Reload catalog
        ↓
        Preserve selected items whenever possible

        ### Offline
        Use cached catalog
        ↓
        Allow browsing
        ↓
        Billing Engine validates before checkout

        *The overarching policy is to favor the latest server truth while minimizing disruption to the user's active session.*

        # 31. Catalog Invariants

        These rules must **ALWAYS** remain true. If any invariant fails, the checkout process must stop immediately.

        - `Quantity >= 1`
        - `Quantity <= 99`
        - Duplicate items never exist in the selected items array (ID uniqueness is maintained).
        - Selected item IDs are unique.
        - Every item belongs to the current business.
        - Inactive items cannot be selected.
        - Deleted items cannot reach checkout.
        - Catalog **never** calculates rewards.
        - Catalog **never** calculates payable amount.
        - Catalog **never** updates wallet.
        - Billing Engine always validates prices.

        ```text
        TanStack Query
        ↓
        Catalog Components
        ↓
        Zustand Billing Store
        ↓
        Billing Engine
        ```

        **Responsibilities:**
        - **Server:** Owns data (database tables).
        - **TanStack Query:** Owns cache (offline resilience, background updates).
        - **Catalog Components:** Own presentation (UI filtering, search).
        - **Billing Store:** Owns selected items (Zustand state).
        - **Billing Engine:** Owns calculations (Math).

        *No layer may violate these responsibilities.*

        # 34. Catalog Change Policy

        Any change to the catalog workflow requires strict governance:

        - Founder approval if the workflow changes.
        - Acceptance Criteria update.
        - Testing Checklist update.
        - Version History update.
        - Engineering review.

        **CRITICAL RULE:** The Catalog module must **never** introduce:
        - Reward logic.
        - Payment logic.
        - Wallet logic.
        - Transaction logic.
        - Billing calculations.
