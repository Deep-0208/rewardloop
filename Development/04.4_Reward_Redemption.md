# 1. Sprint Goal

The objective of Sprint 4.4 is to orchestrate the secure redemption of a customer's loyalty rewards.

The user should be able to:

1. View available reward.
2. View maximum redeemable reward.
3. Enter reward amount.
4. Validate reward (handled via Billing Engine).
5. Verify OTP (if reward > 0).
6. Apply reward.
7. Continue to payment.

The entire flow should complete within 20 seconds to maintain counter speed.

# 3. User Flow

```text
Customer Selected (Sprint 4.1)
        ↓
Catalog Selected (Sprint 4.3)
        ↓
Billing Engine computes subtotal & max redeem
        ↓
Reward Screen
        ↓
Reward Available?
        ├── No  → Continue To Payment
        └── Yes → Enter Reward
                    ↓
                Billing Engine Validation
                    ↓
                OTP Required?
                    ├── No (Reward = 0) → Continue To Payment
                    └── Yes (Reward > 0)
                            ↓
                        OTP Sent via SMS
                            ↓
                        OTP Verified
                            ↓
                        Reward Applied
                            ↓
                        Billing Engine Recalculate
                            ↓
                        Continue To Payment
```

**Alternative Flows:**

- **Cancel OTP:** Tapping "Continue Without Reward" aborts the OTP flow, resets `Reward Applied` to 0, and proceeds to payment.
- **OTP Expired:** Prompts user to resend OTP.
- **OTP Failed:** Alerts incorrect code. After 3 attempts, forces "Continue Without Reward".

## 4.1 Reward Redemption Page

- **Purpose:** Primary interface for entering a reward to redeem.
- **Components:** WalletCard, RewardInput, RewardSummary, ApplyRewardButton, SkipRewardButton.

- **Loading:** Fetching wallet balance.

- **Purpose:** Securely authorize the deduction of customer wallet points.
- **Components:** OTPInput (6 digits), OTPResendTimer, OTPStatus, ContinueWithoutRewardButton.
- **Navigation:** Back to Reward Redemption (resets reward). Forward to Payment.
- **Primary Action:** Verify OTP.
- **Validation:** Exactly 6 digits (numeric only).
- **Loading:** Sending OTP, Verifying OTP.
- **Errors:** Invalid code, expired code, max attempts reached.

# 7. Server Actions

### `getWallet()`

- **Purpose:** Fetch the customer's current wallet balance.
- **Input:** `customerId`, `businessId`.
- **Validation:** Ensure caller is authorized staff for the business.
- **Output:** `{ balance: number }`
- **Errors:** `NOT_FOUND`, `AUTH_ERROR`.
- **Caching:** `['wallet', customerId]`. StaleTime: 0 (must be fresh).

### `validateReward()`

- **Purpose:** Orchestrates with Billing Engine to ensure the entered amount is legal before sending an OTP.
- **Input:** `rewardAmount`, `subtotal`, `customerId`.

### `sendRewardOTP()` — Server Action

- **Purpose:** Generate 6-digit OTP and deliver via MSG91 SMS.
- **File:** `features/reward/actions/send-reward-otp.ts`
- **Input:** `{ customerPhone: string, rewardAmountPaise: number }`
- **Validation:** Rate limits (max 5 OTP requests per phone per 15 minutes).
- **Output:** `{ sent: true, expiresAt: string }`
- **Errors:** `RATE_LIMITED`, `VALIDATION_FAILED`.
- **Side effects:** Inserts `otp_requests` record with bcrypt-hashed OTP.

### `verifyRewardOTP()` — Server Action

- **Purpose:** Validate 6-digit code against hashed DB record.
- **File:** `features/reward/actions/verify-reward-otp.ts`
- **Input:** `{ customerPhone: string, otp: string }`
- **Validation:** Check expiry (3 min), attempt count (max 3), bcrypt hash match.
- **Output:** `{ verified: true, otpRequestId: string }`
- **Errors:** `INVALID_OTP`, `OTP_EXPIRED`, `OTP_MAX_ATTEMPTS`.
- **On success:** Sets `otp_requests.verified_at = now()`.

### `applyReward()` — CLIENT FUNCTION (Not a Server Action)

- **Purpose:** Update the Billing Store's `rewardApplied` value after OTP verification succeeds.
- **File:** Called directly in the OTP verification success handler inside the component.
- **Implementation:** `useBillingStore.getState().setRewardApplied(amount)` and `useBillingStore.getState().setOtpVerifiedToken(otpRequestId)`
- **CRITICAL:** This is a client-side Zustand store update, NOT a Server Action. Server Actions cannot dispatch to client-side state.

### `cancelReward()` — CLIENT FUNCTION (Not a Server Action)

- **Purpose:** Reset OTP state and billing store when user taps "Continue Without Reward".
- **Implementation:** `useBillingStore.getState().setRewardApplied(0)` + `useBillingStore.getState().setOtpVerifiedToken(null)`

# 8. Validation

- **Wallet Exists:** Customer must have a wallet record.
- **Wallet Balance:** Cannot redeem more than current balance.
- **Maximum Redeem:** Cannot redeem more than Billing Engine allows.
- **Reward Amount:** Must be >= 0.
- **OTP Format:** Exactly **6 digits** (numeric only). Standardized across all OTP flows. See Founder Decision 12.
- **OTP Expiry:** Defaults to 3 minutes from generation.
- **OTP Attempts:** Maximum 3 failed attempts per request.
- **OTP Replay:** `verifiedToken` can only be used once during Transaction Save.
- **Manual Reward:** Input must strip decimals and special characters.
- **Continue Without Reward:** Bypasses all validation and sets reward to 0.

---

# 9. OTP Rules

- **Length:** **6 digits** — standardized. Founder Decision 12 locks this. No ambiguity. Supabase Auth default is 6. MSG91 supports 6-digit OTPs.
- **Expiry:** 3 minutes (180 seconds).
- **Attempts:** 3 failed attempts invalidate the code.
- **Resend Delay:** 30 seconds before resend is allowed.
- **Maximum Resends:** 3 times per session.
- **Auto Focus:** Input focuses automatically on mount.
- **Auto Submit:** Submits automatically when the final digit is entered.
- **Paste Support:** Users reading from SMS must be able to paste the code directly.
- **Keyboard Behaviour:** Numeric keypad only (`inputMode="numeric"`).
- **Session Expiry:** If the user leaves the page, the OTP flow cancels.

---

# 10. Reward Rules

- **Reward amount:** Manually entered by staff.
- **Auto Clamp:** Input automatically reduces to `Maximum Redeem` on blur if it exceeds the limit.
- **Maximum Redeem:** Defined by Billing Engine.
- **Minimum Redeem:** ₹1 (if applying a reward).
- **Zero Reward:** Automatically skips the OTP flow.
- **Wallet Empty:** The entire redemption flow is skipped or displays "No rewards available".
- **Continue Without Reward:** Core escape hatch. Sets `RewardApplied = 0`.
- **Reward Reset:** Canceling OTP sets `RewardApplied = 0`.
- **Billing Engine Recalculation:** Occurs immediately after a valid reward is applied.

**Responsibilities:**

- Reward Redemption orchestrates the _user intent_ and _authorization_ (OTP).
- Billing Engine executes the _mathematical consequences_ of that intent.

---

# 11. Billing Engine Integration

**CRITICAL RULE:** Reward Redemption never performs calculations.

Reward Redemption requests data from the Billing Engine via `useBillingStore()`:

- `calculateMaximumRedeem()` (reads state)
- `validateReward()` (relies on store validation logic)
- `calculateFinalAmount()` (reads state preview)
- `calculateRewardEarned()` (reads state preview)

Reward Redemption displays these results only. It mutates state by calling `setRewardApplied(amount)` on the Zustand store, which triggers the Billing Engine's pure functions.

# 13. State Management

## TanStack Query

- `['wallet', customerId]`: Fetches live wallet. StaleTime: 0.
- Mutations for `sendOTP` and `verifyOTP`.

## Zustand (`useBillingStore`)

- Reuses store from Sprint 4.2.
- Actions: `setRewardApplied(amount)`.
- State: `rewardApplied`, `subtotal`, `maxRedeem`.

## Zustand (Local `useOTPStore`)

- Optional, or manage via React state if complex.
- Tracks `otpRequestId`, `otpVerifiedToken`, `resendCountdown`.

## React Hook Form

- Manages `Reward Input` validation.
- Manages `OTP Input` logic and auto-submit.

# 14. State Machine

```text
Wallet Loaded (TanStack Query, staleTime: 0)
        ↓
    (Displays: Available Balance | Max Redeem for this bill)
        ↓
Reward Entered (Manual entry ONLY — no UseMaxButton)
        ↓
Client-side clamp via useBillingStore (display only)
        ↓
    (User taps "Apply Reward")
        ↓
sendRewardOTP() Server Action called
        ↓
OTP Verification Step shown
        ├── User taps "Continue Without Reward"
        │       → cancelReward() [client fn]
        │       → rewardApplied = 0, otpVerifiedToken = null
        │       → Advance to checkout step
        ├── OTP Expires → User taps Resend
        │       → sendRewardOTP() called again (30s cooldown enforced)
        ├── OTP Fails 3x
        │       → OTP_MAX_ATTEMPTS error
        │       → Force "Continue Without Reward" path
        └── OTP Verified (verifyRewardOTP() Server Action)
                ↓
            applyReward() [client fn] → useBillingStore.setRewardApplied(amount)
            setOtpVerifiedToken(otpRequestId) → stored in Zustand
                ↓
            Billing Engine recalculates (all values update in Zustand)
                ↓
            Advance to checkout step (useBillingStore.setStep('checkout'))
```

# 18. Edge Cases

- **Wallet becomes zero during selection:** Server-side validation during `completeBilling()` will catch this race condition.
- **Reward > wallet:** UI auto-clamps to wallet balance.
- **Reward > max redeem:** UI auto-clamps to max redeem.
- **OTP timeout:** Handled gracefully. Screen stays open, input disabled until user requests resend.
- **OTP resend spam:** Backend rate limit (e.g., 3 per 5 mins). Frontend timer (30s).
- **Offline:** Cannot send/verify OTP. Must disable reward application and force full payment.
- **Refresh page:** Standard behavior (reset flow, return to catalog/billing state).
- **Duplicate OTP verification:** Once verified, the token is stored in Zustand. Subsequent calls bypass verification.
- **Rapid button presses:** `isLoading` states disable buttons.

---

# 19. Security

- **Server validates reward:** The final `completeBilling` action recalculates everything. The client is untrusted.
- **Server validates OTP:** Verification happens purely on the backend.
- **Prevent replay attacks:** OTP tokens are single-use and tied to the specific transaction request.
- **Prevent OTP reuse:** Expire OTPs immediately upon successful verification or max attempts.
- **Rate limit OTP:** Protect SMS gateway costs and prevent SMS bombing.
- **Business isolation:** OTP requests are tied to the specific `businessId`.
- **Server owns reward truth:** The wallet balance on the client is purely informational.
- **Client only displays state:** No math on the client.

# 28. AI Coding Instructions

**Every AI-generated implementation must:**

- **Reuse Billing Engine:** Read from `useBillingStore`.
- **Never calculate rewards locally:** Do not attempt `Subtotal - Reward`.
- **Never calculate payable amount:** Just read `finalAmount`.
- **Never update wallet directly:** Updating `reward_wallets` happens in the Server Action during transaction save, not here.
- **Always call Billing Engine:** Trust its constraints.
- **Always validate on server:** The OTP action must securely verify the code against the database.
- **Never duplicate business logic:** Separation of concerns is absolute.
- **Strict TypeScript:** Use exact types for OTP payloads and API responses.
- **Use Zod:** For all Server Action payload validation.
- **Follow Founder Decisions:** Explicitly Decision 12 (OTP required for redemption).

---

# 29. Reward Redemption Invariants

These mathematical and workflow rules must **always remain true**:

- `Reward Applied >= 0`
- `Reward Applied <= Wallet Balance`
- `Reward Applied <= Maximum Redeem`
- OTP is required **only** when `Reward Applied > 0`.
- "Continue Without Reward" must strictly set `Reward Applied = 0` and bypass OTP.
- The Billing Engine is the ultimate validator of the reward amount.
- The client NEVER owns the reward truth (server recalculates).
- Wallet updates occur ONLY after a successful transaction commit (Sprint 4.5), never during redemption.

If any invariant fails, redemption must stop immediately.
