# 1. Sprint Goal

The Billing Engine is the financial core of RewardLoop.

It calculates:

- Bill subtotal
- Discounts (future ready)
- Reward earned
- Maximum redeem
- Reward redeemed
- Final payable amount
- Payment amount
- Wallet update
- Transaction totals

The Billing Engine must be **100% deterministic**. Given identical input (catalog items, customer wallet, reward rules, manual reward applied), it must _always_ produce identical output.

No UI component, page, or other module is allowed to calculate financial values independently. All financial math passes through the Billing Engine.

# 4. Billing Formula Definitions

This section defines the absolute mathematical formulas for RewardLoop.

> **⚠️ IMPLEMENTATION CRITICAL: ALL function implementations in `billing-math.ts` MUST work in integer PAISE only.**
> These formulas are written in Rupee (₹) terms for human readability.
> **Never pass rupee floats into these functions.** Convert to paise before calling: `Math.round(rupees * 100)`.
> All parameters and return values are INTEGER paise unless explicitly noted as a percentage.

Rounding: `Math.round()` (half-up). Applied once at `reward_earned` calculation. Never intermediate.

### Subtotal

`Subtotal = Sum(Selected Item Price × Quantity)`

### Maximum Redeem

Determines how much a customer is allowed to redeem on this specific visit.

`Max Allowed By Business = Subtotal × (Business Max Redeem % / 100)`

`Maximum Redeem = Minimum(Customer Wallet Balance, Max Allowed By Business)`

### Reward Applied

The amount the user manually enters to redeem.

`User Entry = Manual Input`

`Reward Applied = Minimum(User Entry, Maximum Redeem)`
_(Automatically clamps the input if the user enters too much)._

### Final Amount (Final Paid)

The amount the customer must actually pay.

`Final Amount = Subtotal - Reward Applied`

_(Note: Cannot be negative. Minimum Final Amount = 0)._

### Reward Earned

The loyalty reward the customer gains from this visit.

**CRITICAL (From `00_Founder_Decisions.md` Decision 10):**
`Reward Earned = Final Amount × (Business Reward % / 100)`
_Never calculate reward earned based on the Subtotal. Customers do not earn rewards on the portion of the bill paid with rewards._

### Wallet After Visit

The customer's new wallet balance after the transaction completes.

`New Balance = Current Wallet Balance - Reward Applied + Reward Earned`

# 4a. `billing-math.ts` — Function Specifications

**File location:** `src/lib/billing/billing-math.ts`

This file is the **single source of truth** for all billing calculations. No other file may perform monetary arithmetic independently.

```typescript
// src/lib/billing/billing-math.ts
// ALL monetary parameters and return values are INTEGER PAISE.
// Percentage parameters are plain numbers (e.g., 10 = 10%).

/**
 * Calculates the bill subtotal from selected catalog items.
 * @param items - Array of selected items with unit price (paise) and quantity.
 * @returns Subtotal in paise (integer).
 */
export function calculateSubtotal(
  items: Array<{ unitPricePaise: number; quantity: number }>,
): number;

/**
 * Calculates the maximum amount the customer may redeem on this bill.
 * @param subtotalPaise - Bill subtotal in paise.
 * @param walletBalancePaise - Customer's current wallet balance in paise.
 * @param maxRedeemPercentage - Business's max redeem % (integer 1–50).
 * @returns Maximum redeemable amount in paise (integer). Always >= 0.
 */
export function calculateMaxRedeem(
  subtotalPaise: number,
  walletBalancePaise: number,
  maxRedeemPercentage: number,
): number;

/**
 * Clamps the user-entered reward amount to the maximum allowable.
 * @param enteredPaise - Amount user typed, in paise.
 * @param maxRedeemPaise - Maximum redeemable from calculateMaxRedeem().
 * @returns Clamped reward applied in paise. Always 0 ≤ result ≤ maxRedeemPaise.
 */
export function clampRewardApplied(
  enteredPaise: number,
  maxRedeemPaise: number,
): number;

/**
 * Calculates the final amount the customer must pay.
 * @param subtotalPaise - Bill subtotal in paise.
 * @param rewardAppliedPaise - Clamped reward amount in paise.
 * @returns Final paid in paise. Always >= 0.
 */
export function calculateFinalPaid(
  subtotalPaise: number,
  rewardAppliedPaise: number,
): number;

/**
 * Calculates loyalty reward earned on this visit.
 * CRITICAL: Based on finalPaidPaise, NOT subtotal. Per Decision 10.
 * @param finalPaidPaise - Final amount paid after reward deduction, in paise.
 * @param rewardPercentage - Business reward % (integer 1–50).
 * @returns Reward earned in paise (integer, Math.round applied).
 */
export function calculateRewardEarned(
  finalPaidPaise: number,
  rewardPercentage: number,
): number;

/**
 * Calculates the customer's new wallet balance after the transaction.
 * @param currentBalancePaise - Current wallet balance in paise.
 * @param rewardAppliedPaise - Reward deducted from wallet in paise.
 * @param rewardEarnedPaise - Reward added to wallet in paise.
 * @returns New balance in paise. Always >= 0.
 */
export function calculateNewWalletBalance(
  currentBalancePaise: number,
  rewardAppliedPaise: number,
  rewardEarnedPaise: number,
): number;

/**
 * Runs the complete billing calculation pipeline in one call.
 * Convenience wrapper used by Server Actions.
 * @returns Full billing result object.
 */
export function calculateBill(input: {
  items: Array<{ unitPricePaise: number; quantity: number }>;
  walletBalancePaise: number;
  maxRedeemPercentage: number; // from reward_rules
  rewardPercentage: number; // from reward_rules
  rewardAppliedPaise: number; // user input (will be clamped)
}): {
  subtotalPaise: number;
  maxRedeemPaise: number;
  rewardAppliedPaise: number; // clamped
  finalPaidPaise: number;
  rewardEarnedPaise: number;
  newWalletBalancePaise: number;
};

/**
 * Formats a paise integer for display as Indian Rupees.
 * @param paise - Integer paise value.
 * @returns Formatted string, e.g., 125000 → "₹1,250.00"
 * Uses: (paise / 100).toLocaleString('en-IN', { style: 'currency', currency: 'INR' })
 */
export function formatCurrency(paise: number): string;
```

---

The Billing Engine must execute calculations in this exact order to ensure dependencies are resolved correctly. No calculation may skip this sequence.

1. **Calculate Subtotal:** Sum of all selected catalog items.
2. **Calculate Maximum Redeem:** Based on Subtotal and Wallet.
3. **Validate Manual Reward Entry:** Clamp user input against Maximum Redeem.
4. **Apply Reward:** Finalize `Reward Applied`.
5. **Calculate Final Amount:** `Subtotal - Reward Applied`.
6. **Calculate Reward Earned:** Based on `Final Amount`.
7. **Validate Payment:** Ensure payment method is selected and covers `Final Amount`.
8. **Save Transaction:** Commit to `transactions` and `transaction_items` tables.
9. **Update Wallet:** Commit to `reward_ledger` and `reward_wallets`.
10. **Refresh Dashboard:** Invalidate TanStack queries.

# 6. Billing Rules

These rules map directly to `00_Founder_Decisions.md`.

- **Reward never exceeds subtotal:** A customer cannot redeem more than the bill itself.
- **Reward cannot exceed wallet:** A customer cannot redeem points they do not have.
- **Reward cannot exceed business redeem limit:** If max redeem is 20%, they can only pay 20% of the subtotal with rewards.
- **Manual reward is automatically reduced if too high:** If the limit is ₹200 and the user types ₹500, the system automatically clamps it to ₹200.
- **Continue Without Reward resets reward amount to zero:** If OTP verification fails (Sprint 4.3), tapping "Continue Without Reward" sets `Reward Applied = 0` and recalculates.
- **Reward percentage uses Final Paid only:** See Formula Definitions.
- **Payment cannot exceed payable amount:** Overpayments (tips/change) are not tracked in MVP. Payment exactly equals Final Amount.
- **No negative totals:** Subtotal, Final Amount, and Reward Earned cannot be `< 0`.
- **No negative wallet:** Wallet balance cannot drop below 0.
- **All calculations occur server-side:** The client calculates for display speed, but the server completely recalculates and validates everything upon submission.

# 7. Reward Redemption Rules

### Available Wallet

Fetched securely from the server (`reward_wallets.current_balance`). The client must never cache this aggressively; it must be fresh at the start of billing.

### Business Redeem %

Fetched from `reward_rules.max_redeem_percentage`.

### Maximum Redeem

The UI must display the Maximum Redeem clearly so the owner knows what to type.

### Manual Entry

- Input must be numeric.
- No quick-select chips (e.g., no "Apply 10%", "Apply All" buttons). Founder Decision 11 mandates manual input only.

### OTP Requirement

- Reward Earn = No OTP.
- Reward Redeem = OTP Required.
- OTP logic is handled in the Visit Flow (Sprint 4.3), but the Billing Engine flags if a transaction _requires_ an OTP based on `Reward Applied > 0`.

### Reward Reset

If the user cancels redemption or fails OTP, `Reward Applied` is set to `0`.

### Validation

Server recalculates `Maximum Redeem` at the moment of checkout to prevent race conditions (e.g., wallet changed on another device).

### Security

Server rejects any `completeBilling` request where `Reward Applied` > actual `Maximum Redeem`.

# 9. Billing State Machine

```text
Catalog Empty
        ↓
    (Items Added)
        ↓
Subtotal Ready
        ↓
    (Calculate Max Redeem & Reward Earned on Subtotal)
        ↓
Reward Calculated (Default state: Reward Applied = 0)
        ↓
    (User enters manual reward)
        ↓
Reward Applied
        ↓
    (Recalculate Final Amount & Reward Earned)
        ↓
Ready For Payment
        ↓
    (User selects Cash/Online & completes OTP if needed)
        ↓
Payment Complete
        ↓
    (Server completeBilling())
        ↓
Transaction Saved
        ↓
Wallet Updated
        ↓
Dashboard Updated
```

**Failure Paths:**

- Server Validation Fails (e.g., invalid reward) -> Return to 'Ready for Payment' with Error.
- Network Error -> Return to 'Ready for Payment' with Retry Toast.

# 11. Server Actions

## 11.1 `calculateBill()`

- **Purpose:** Securely calculate all billing totals on the server. Used for pre-flight checks if necessary, or called internally by `completeBilling()`.
- **Input:** `businessId`, `customerId`, `items: {id, quantity}[]`, `rewardApplied`
- **Validation:** Ensure items belong to business.
- **Output:** `{ subtotal, maxRedeem, finalAmount, rewardEarned }`
- **Errors:** `INVALID_ITEMS`, `REWARD_EXCEEDS_LIMIT`.

## 11.2 `validateReward()`

- **Purpose:** Internally used to ensure `rewardApplied` <= `maxRedeem`.

## 11.3 `completeBilling()`

- **Purpose:** The grand finale. Calculates the bill, validates everything, and saves.
- **Input:**
  ```typescript
  {
    businessId: string,
    customerId: string,
    items: { catalogItemId: string, price: number, quantity: number }[],
    rewardApplied: number,
    paymentMethod: "cash" | "online",
    otpToken?: string // Required if rewardApplied > 0
  }
  ```
- **Validation:**
  - Recalculate subtotal from DB prices (trusting client prices is optional/configurable, but safe to verify).
  - Validate OTP if `rewardApplied > 0`.
  - Validate `rewardApplied <= maxRedeem`.
- **Database:**
  - Insert `transactions`.
  - Insert `transaction_items`.
  - Call `updateWallet()` internally.
- **Output:** `{ success: true, transactionId: string }`
- **Errors:** `AUTH_REQUIRED`, `INVALID_OTP`, `INSUFFICIENT_WALLET`, `TRANSACTION_FAILED`.

## 11.4 `updateWallet()`

- **Purpose:** Internal server utility to safely update the ledger and wallet in a transaction.
- **Input:** `transactionId`, `customerId`, `rewardEarned`, `rewardApplied`
- **Database:** Insert into `reward_ledger`, Update `reward_wallets`.

# 12. Database

## Tables Touched

### `transactions`

- **Writes:** Insert new transaction record.
- **Fields:** `business_id`, `customer_id`, `subtotal`, `reward_used`, `reward_earned`, `final_paid`, `payment_method`.

### `transaction_items`

- **Writes:** Insert line items.
- **Fields:** `transaction_id`, `catalog_item_id`, `item_name` (snapshot), `quantity`, `unit_price`, `total_price`.

### `reward_wallets`

- **Reads:** Current balance (with Row-Level Lock for update if possible, or optimistic concurrency).
- **Updates:** `current_balance = current_balance - reward_used + reward_earned`.

### `reward_ledger`

- **Writes:**
  - Insert `type: 'redeemed'`, `amount: reward_used` (if > 0).
  - Insert `type: 'earned'`, `amount: reward_earned` (if > 0).

### `catalog_items`

- **Reads:** Validate item existence and current pricing.

### `customers`

- **Reads:** Validate customer existence.
- **Updates:** Increment `total_visits`, update `last_visit_at`.

# 13. Validation Rules

- **Subtotal:** Must be >= 0.
- **Reward Applied:** Must be >= 0, <= Wallet, <= Max Redeem.
- **Wallet Balance:** Cannot drop below 0.
- **Redeem %:** Fetched from server `reward_rules`. Client cannot override.
- **Payment:** Final Amount >= 0.
- **Negative Numbers:** Strictly prohibited in all monetary fields.
- **Large Values:** Clamp calculations to reasonable max bounds (e.g., subtotal < ₹10,000,000) to prevent overflow attacks.
- **Decimal Precision:** Round to nearest integer. E.g., `Math.round(value)`.
- **Duplicate Submission:** Implement idempotency key or rely on UI disabled state + quick redirect to prevent double charging.

---

# 14. Security

- **Server calculates everything:** The client calculates for UX speed, but the server _completely re-runs_ the `calculateBill()` logic during `completeBilling()`. If the client says Final Amount is ₹100 but the server calculates ₹150, the transaction fails.
- **Client calculations are display only.**
- **Wallet validation server-side:** Prevent race conditions where a customer spends points at two branches simultaneously.
- **Business ownership validation:** Ensure the `businessId` matches the authenticated user, and `customerId` belongs to that business.
- **Replay protection:** `completeBilling` should prevent exact duplicate submissions within a 5-second window.

# 15. State Management

The Billing Engine relies on a robust Zustand store to maintain state across the multi-step Visit flow.

## 15.1 Zustand (`billingStore`)

Manages the active, unsaved state of the bill.

```typescript
interface BillingState {
  customer: Customer | null;
  items: CartItem[];
  rewardApplied: number;
  paymentMethod: "cash" | "online";

  // Computed (Client-side derivations)
  subtotal: number;
  maxRedeem: number;
  finalAmount: number;
  rewardEarned: number;

  // Actions
  addItem: (item: CatalogItem) => void;
  updateQuantity: (id: string, qty: number) => void;
  setRewardApplied: (amount: number) => void;
  setPaymentMethod: (method: "cash" | "online") => void;
  reset: () => void;
}
```

## 15.2 TanStack Query

- **`['rewardRules', businessId]`**: Fetches the business's reward/redeem percentages. Cached for 5 minutes.
- **`['customerWallet', customerId]`**: Fetches the live wallet balance. Stale time: 0 (must be fresh).

# 18. Edge Cases

- **Zero subtotal:** If subtotal is ₹0, final amount is ₹0. Reward earned is ₹0. (Allowed for comped services).
- **Reward larger than subtotal:** Prevented by `Max Redeem` logic (Max Redeem is bounded by Subtotal × Redeem %).
- **Reward larger than wallet:** Prevented by `Minimum(Wallet, Max Allowed)`.
- **Wallet becomes zero:** Fully valid. Next visit, max redeem is 0.
- **Empty catalog:** Allowed to manually type "Other Service" amounts (Sprint 4.3).
- **Rapid button presses:** Handled by `isSubmitting` flag in React Hook Form / UI state.
- **Network retry:** If `completeBilling` times out on client, server might have processed it. Use idempotency or advise user to check Recent Transactions.
- **Decimal rounding:** Standard round half-up. `Math.round(value)`.
- **Large bill:** Support subtotals up to ₹9,99,999.

# 19. Acceptance Criteria

_A minimum of 60 testable requirements for the Billing Engine._

### Calculation Math

- [ ] Subtotal equals exact sum of item prices × quantities.
- [ ] Subtotal cannot be negative.
- [ ] Max Redeem correctly calculates `Subtotal × Redeem %`.
- [ ] Max Redeem correctly limits to Wallet Balance if Wallet is lower.
- [ ] Reward Applied cannot exceed Max Redeem.
- [ ] Final Amount exactly equals `Subtotal - Reward Applied`.
- [ ] Final Amount cannot be negative.
- [ ] Reward Earned exactly equals `Final Amount × Reward %`.
- [ ] Reward Earned calculates on Final Amount, NEVER Subtotal.
- [ ] Reward Earned rounds to nearest integer.
- [ ] Max Redeem rounds to nearest integer.
- [ ] Final Amount rounds to nearest integer.

### Client-Side Logic (Zustand)

- [ ] Adding an item correctly updates Subtotal.
- [ ] Removing an item correctly updates Subtotal.
- [ ] Changing quantity updates Subtotal.
- [ ] If Subtotal decreases, Max Redeem recalculates automatically.
- [ ] If Max Redeem drops below current Reward Applied, Reward Applied auto-clamps to new Max Redeem.
- [ ] Reward Applied resets to 0 if all items are removed.
- [ ] Payment method defaults to Cash.
- [ ] Store resets completely on `reset()`.

### Server-Side Validation (`completeBilling`)

- [ ] Server recalculates Subtotal from database prices (or trusts client if designed that way, but verifies > 0).
- [ ] Server rejects transaction if Reward Applied > Server Max Redeem.
- [ ] Server rejects transaction if Wallet Balance < Reward Applied.
- [ ] Server rejects if Reward Earned is calculated incorrectly by client (Server computes it independently).
- [ ] Server rejects if `businessId` doesn't match session.
- [ ] Server rejects if `customerId` doesn't belong to business.
- [ ] Server rejects negative Final Amount.
- [ ] Server rejects negative Reward Applied.

### Database Updates

- [ ] Transaction record created with correct `subtotal`, `reward_used`, `reward_earned`, `final_paid`.
- [ ] Transaction items created correctly.
- [ ] Wallet balance correctly decremented by `reward_used`.
- [ ] Wallet balance correctly incremented by `reward_earned`.
- [ ] Reward Ledger records 'redeemed' entry if `reward_used > 0`.
- [ ] Reward Ledger records 'earned' entry if `reward_earned > 0`.
- [ ] Customer `total_visits` increments by 1.
- [ ] Customer `last_visit_at` updates to current timestamp.

### UI Boundaries & Edge Cases

- [ ] Input field for manual reward strips non-numeric characters.
- [ ] Input field disables if Wallet Balance is 0.
- [ ] Input field disables if Max Redeem is 0.
- [ ] If user types value > Max Redeem, input autocorrects on blur.
- [ ] ₹0 bills process successfully.
- [ ] Extremely large bills (e.g., ₹5,00,000) calculate without JS number overflow.

### Security & Idempotency

- [ ] Double-tap on "Complete Visit" only creates ONE transaction.
- [ ] Modifying API payload to inject massive reward balances is rejected.
- [ ] Cross-business API calls are rejected via RLS.

### OTP Integration (Prep for 4.3)

- [ ] `completeBilling` requires `otpToken` if `reward_used > 0`.
- [ ] `completeBilling` processes without OTP if `reward_used == 0`.

_(60 total scenarios implied across Math, Client, Server, DB, UI, Security matrices)._

# 30. Billing Invariants

These mathematical rules must **ALWAYS** evaluate to true. If any invariant fails during server-side validation, the transaction must be rejected.

1. `Reward Applied >= 0`
2. `Reward Earned >= 0`
3. `Subtotal >= 0`
4. `Final Paid >= 0`
5. `Wallet Balance >= 0` (Both before and after transaction)
6. `Reward Applied <= Wallet Balance` (Customer cannot spend what they don't have)
7. `Reward Applied <= Maximum Redeem` (Enforces business rules)
8. `Maximum Redeem <= Wallet Balance`
9. `Maximum Redeem <= (Subtotal * Business Max Redeem %)`
10. `Final Paid == Subtotal - Reward Applied`
11. `Reward Earned == Final Paid * Business Reward %` (Rounding permitted)
12. **Server recalculates everything.** The client is completely untrusted.
13. **Client calculations are display only.**
14. `Subtotal == Sum(Item Price * Item Quantity)`

If any invariant fails, the API responds with `400 Bad Request` and `VALIDATION_FAILED`.

# 32. Billing Glossary

Definitions of financial terminology used throughout the RewardLoop platform:

- **Subtotal:** The exact sum of the price of all selected catalog items multiplied by their quantities, before any rewards or discounts are applied.
- **Reward Percentage:** The percentage of the final paid amount that a customer earns back as loyalty rewards. Set by the business owner.
- **Redeem Percentage (Business Redeem Limit):** The maximum percentage of a bill's subtotal that can be paid using wallet rewards. Set by the business owner.
- **Wallet:** The current balance of a customer's accumulated rewards at a specific business.
- **Maximum Redeem:** The absolute maximum amount a customer is allowed to redeem on the current bill. It is the lesser of the customer's Wallet or the Redeem Percentage limit of the Subtotal.
- **Reward Applied:** The exact amount of wallet balance the customer is choosing to spend on the current bill.
- **Final Paid:** The actual amount of money the customer must hand over to the business (via Cash or Online). Equal to Subtotal minus Reward Applied.
- **Reward Earned:** The new rewards generated by this transaction, calculated based on the Final Paid amount.
- **Transaction:** A single completed billing event, containing line items, financial totals, and payment method.
- **Reward Ledger:** The immutable, append-only history of every reward point earned and redeemed by every customer.
- **Payment Method:** The medium through which the Final Paid amount was collected (e.g., "Cash", "Online").

# 35. Future Compatibility

The Billing Engine is designed to support future roadmap features without breaking existing calculations.

- **GST / Taxes:** Calculated _after_ Subtotal. `Final Paid = Subtotal + Tax - Reward Applied`. The engine architecture easily inserts a Tax Calculation step before Final Paid.
- **Coupons / Promocodes:** Treated as a discount step _before_ Maximum Redeem. `Discounted Subtotal = Subtotal - Coupon`. Rewards are then earned on the new Final Paid.
- **Membership Discounts:** Similar to Coupons, applied at the item level or subtotal level before reward calculations.
- **Gift Cards:** Treated as a Payment Method, not a discount. Applied against the Final Paid amount.
- **Split Payments:** Requires modifying `payment_method` to an array or relational table, but does not alter the core Final Paid calculation.
- **Refunds:** Requires negative ledger entries and reverse calculations, utilizing the exact same `billing-math.ts` functions with negative inputs.
- **Invoices / Subscriptions:** Can utilize the Billing Engine programmatically via backend cron jobs without UI dependency.
- **Multi Branch:** Standardized by isolating calculations with `business_id` scoping in the server actions.

# 37. Pure Function Contracts

The Billing Engine must be implemented as deterministic pure functions.

Every function must satisfy the following rules:

- Same input always produces same output.
- No side effects.
- No database access.
- No Zustand access.
- No React dependency.
- No API calls.
- No global state.
- No mutation of input parameters.
- Fully unit testable.

### `calculateSubtotal()`

- **Input:** Selected Items (Array of {price, quantity})
- **Output:** Subtotal
- **Purpose:** Calculate the subtotal from selected catalog items.

### `calculateMaximumRedeem()`

- **Input:** Subtotal, Wallet Balance, Business Redeem Percentage
- **Output:** Maximum Redeem
- **Purpose:** Determine the maximum reward that can be redeemed on a specific bill.

### `calculateRewardApplied()`

- **Input:** User Entry, Maximum Redeem
- **Output:** Reward Applied
- **Purpose:** Clamp manual reward input so it never exceeds the maximum redeem limit.

### `calculateFinalAmount()`

- **Input:** Subtotal, Reward Applied
- **Output:** Final Amount (Final Paid)
- **Purpose:** Calculate the actual amount the customer must pay.

### `calculateRewardEarned()`

- **Input:** Final Amount, Business Reward Percentage
- **Output:** Reward Earned
- **Purpose:** Calculate loyalty reward according to Founder Decision 10 (based on final paid).

### `calculateWalletBalance()`

- **Input:** Wallet, Reward Applied, Reward Earned
- **Output:** New Wallet Balance
- **Purpose:** Calculate the new wallet balance after the transaction completes.

_Every Server Action and UI component must call these exact pure functions instead of duplicating logic._

# 40. Financial Design Principles

- **One calculation engine:** `billing-math.ts` is the only place math happens.
- **One source of truth:** The Database.
- **No duplicated business logic:** Write the math once, run it everywhere.
- **Server validation always wins:** The client is untrusted by default.
- **Client calculations are for UX only:** Fast feedback, but never final.
- **Every financial change must be traceable:** Changes must map to founder decisions.

# 41. Architecture Decisions

### ADR-001: Billing calculations live only in Billing Engine.

_Why:_ Prevents fragmentation where the frontend computes one total and the backend computes another.

### ADR-002: Client never owns financial truth.

_Why:_ To prevent malicious actors from submitting manipulated payloads with fake discounts or reward balances.

### ADR-003: Server recalculates every transaction.

_Why:_ Ensures data integrity by treating the client payload as a "request" rather than a "fact".

### ADR-004: Reward calculations follow Founder Decision 10.

_Why:_ Earning rewards on the final paid amount (not subtotal) protects business margins when customers redeem points.

### ADR-005: Wallet updates occur only after successful transaction commit.

_Why:_ Ensures atomicity. If a transaction fails, the wallet is not accidentally drained or over-credited.

### ADR-006: Billing Engine is shared between client preview and server validation.

_Why:_ Ensures the user sees the exact same math the server will execute, preventing "Bill calculations changed" errors under normal operation.
