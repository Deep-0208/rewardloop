# 1. Sprint Goal

The objective of Sprint 4.5 is to finalize the customer visit securely and reliably.

The user should be able to:

1. Review Bill
2. Select Payment Method
3. Complete Payment
4. Save Transaction
5. Update Wallet
6. Refresh Dashboard
7. Return to Home

The entire process should complete within 10 seconds to ensure a fast counter experience.

```text

        ↓

        ↓
Select Payment Method
        ↓
Tap Complete Visit
        ↓
Server Validation
        ↓
Transaction Saved
        ↓
Reward Ledger Updated
        ↓
Wallet Updated
        ↓
Dashboard Cache Invalidated
        ↓
Success
        ↓
Dashboard
```

**Alternative Flows:**

- **Network failure:** Show error toast, allow retry.
- **Duplicate submission:** Idempotency key prevents duplicate, returns existing success state.
- **Session expiry:** Redirect to login; save state locally if possible.
- **Server error:** Rollback transaction, show error banner, allow retry.
- **Refresh during save:** Backend completes atomic save, frontend loads fresh state on reconnect.
- **Browser close:** Backend completes atomic save.

# 6. Database

## Tables Touched

### `transactions`

- **Writes:** Insert new transaction (`subtotal`, `final_paid`, `reward_used`, `reward_earned`, `payment_method`).
- **Indexes:** `business_id + created_at` (for dashboard).

### `transaction_items`

- **Writes:** Insert all catalog items associated with the transaction.

### `reward_wallets`

- **Reads:** Lock row for update.
- **Updates:** `balance = balance - reward_used + reward_earned`.

### `reward_ledger`

- **Writes:** Insert 'earned' entry (if >0) and 'redeemed' entry (if >0).

### `customers`

- **Updates:** `total_visits = total_visits + 1`, `last_visit_at = now()`.

### `businesses`

- **Reads:** Validate business existence and active status.

**CRITICAL RULE:** All writes and updates must occur within a single ACID-compliant database transaction using Supabase RPC or server-side transaction blocks.

# 7. Server Actions

### `completeVisit()`

- **Purpose:** The primary orchestrator for the entire save process.
- **Input:** `customerId`, `businessId`, `items`, `rewardApplied`, `otpToken` (if required), `paymentMethod`, `idempotencyKey`.
- **Validation:**
  - Recalculates everything via Billing Engine.
  - Verifies OTP token if `rewardApplied > 0`.
- **Database:** Calls the internal functions within an atomic transaction.
- **Output:** `{ success: true, transactionId: string }`
- **Errors:** `VALIDATION_FAILED`, `OTP_INVALID`, `WALLET_INSUFFICIENT`, `DATABASE_ERROR`.
- **Rollback behavior:** Any failure rolls back all database changes entirely.

### Internal DB Helpers (Invoked by `completeVisit`)

- `saveTransaction()`
- `saveTransactionItems()`
- `updateRewardWallet()`
- `createRewardLedger()`

### `refreshDashboard()`

- **Purpose:** Trigger revalidation of cached dashboard routes (Next.js `revalidatePath` or `revalidateTag`).

# 8. Transaction Sequence

The exact execution order required on the server:

1. Validate Session
2. Validate Customer
3. Validate Catalog (Items exist, prices valid)
4. Billing Engine Recalculate (Server computes truth)
5. Validate Reward (Balance >= reward_used, OTP valid if >0)
6. BEGIN DATABASE TRANSACTION
7. Create Transaction
8. Create Transaction Items
9. Create Reward Ledger
10. Update Wallet
11. Update Customer Statistics
12. COMMIT DATABASE TRANSACTION
13. Invalidate Queries (Next.js Cache / TanStack Query)
14. Navigate Dashboard

**No step may execute out of order.**

# 9. Payment Rules

- **Cash:** Physical cash accepted. No external validation required.
- **Online:** UPI, Cards, NetBanking. (For MVP, the app assumes the staff verified the online payment externally, e.g., checked their Soundbox or PhonePe app).
- **Validation:** A payment method must be selected if `Final Paid > 0`. If `Final Paid == 0`, payment method defaults to "None" or is ignored.
- **Default selection:** Cash (optimizes for speed).
- **Future payment methods:** The architecture must allow adding 'Gift Card' or 'Split Payment' simply by expanding the `paymentMethod` enum.

**Responsibilities:**
RewardLoop tracks the _recording_ of the payment, not the _processing_ of the payment (MVP).

---

# 10. Transaction Integrity

- **Atomic database transaction:** A failure in step 11 must roll back step 7.
- **Rollback policy:** All-or-nothing. No partial saves.
- **Idempotency:** The client generates a unique UUID (Idempotency Key) when opening the checkout. The server rejects duplicate requests with the same key.
- **Duplicate prevention:** Client UI disables the submit button immediately upon tap.
- **Server validation:** The client payload is treated as a request, not a fact. The server recalculates all financial totals.
- **Audit trail:** The `reward_ledger` serves as the immutable audit trail for the `reward_wallets`.
- **Consistency guarantees:** Wallet balance must exactly equal the sum of all ledger entries for that customer.

| --------------------- | --------------------------- | ------------------------------ |
| Duplicate Transaction | Idempotency key reused      | Redirect to success/dashboard  |

# 17. Edge Cases

- **Double tap Complete:** UI overlay blocks it. Idempotency key blocks it on the server.
- **Refresh during save:** Backend processes transaction. User returns to a fresh catalog but the transaction is safely on the dashboard.
- **Offline:** Submit button disabled or throws immediate network error. Must have network to save.
- **Large bill:** Server easily handles large numbers up to DB limits.
- **Wallet update race:** Customer checks out at two registers simultaneously. Postgres Row-Level Locks or atomic updates (`balance = balance - X`) prevent negative balances.
- **Server timeout:** Client handles timeout error, informs user to check Recent Transactions before retrying.
- **Retry:** Works safely due to idempotency keys.
- **Back navigation:** Blocked during `isSubmitting`.
- **Multiple tabs:** Supported, isolated by Zustand state (though not recommended for staff).

---

# 18. Security

- **Server owns transaction truth:** The server completely re-runs the Billing Engine before saving.
- **Billing Engine recalculates before save:** Client totals are ignored.
- **OTP must already be verified:** The server checks the valid OTP token before applying rewards.
- **Business isolation:** RLS (Row Level Security) and application logic ensure transactions only link to the authenticated user's business.
- **Audit logging:** Reward ledger tracks every point movement.
- **Idempotency keys:** Prevents double-charging customers.

# 27. AI Coding Instructions

**Every AI-generated implementation must:**

- **Never calculate money:** The Server Action must call `calculateFinalAmount` from `billing-math.ts`.
- **Always call Billing Engine:** The Server Action relies on Sprint 4.2's math.
- **Never bypass server validation:** Client totals are purely visual.
- **Use one atomic database transaction:** `BEGIN` ... `COMMIT`. If any step fails, `ROLLBACK`.
- **Never partially save data:** Do not save a transaction without updating the wallet.
- **Always invalidate dashboard queries after success:** Ensure the user sees live data upon return.
- **Maintain strict TypeScript:** Type the complex transaction payload precisely.

# 28. Transaction Invariants

These architectural rules must never be violated during save:

- Transaction ID is unique (UUID).
- Transaction total equals Billing Engine output EXACTLY.
- Wallet balance never becomes negative.
- Reward ledger entries always perfectly match the wallet update `(Earned - Redeemed)`.
- Transaction records and ledger records are committed together atomically.
- No duplicate submissions are permitted (Idempotency Key).
- Dashboard refreshes automatically after a successful commit.

# 30. Database Transaction Timeline

The exact lifecycle of the Complete Visit database transaction:

Customer taps Complete Visit
↓
Server Action Starts
↓
BEGIN DATABASE TRANSACTION (Lock Acquired on connection)
↓
Lock Reward Wallet (SELECT FOR UPDATE)
↓
Validate Session
↓
Validate Customer
↓
Billing Engine Recalculate
↓
Validate Reward Redemption
↓
Insert Transaction
↓
Insert Transaction Items
↓
Insert Reward Ledger
↓
Update Reward Wallet
↓
Update Customer Statistics
↓
COMMIT
↓
Release Locks (Automatic upon commit)
↓
Invalidate Dashboard Queries
↓
Navigate Dashboard

**Locking Policy:**

- Locks begin at `BEGIN DATABASE TRANSACTION` + `SELECT FOR UPDATE` on the specific `reward_wallets` row.
- Locks are released immediately upon `COMMIT` or `ROLLBACK`.

# 31. Idempotency Policy

- **Idempotency Key generation:** UUIDv4 generated securely on the client.
- **When it is created:** The moment the Complete Visit screen (checkout phase) mounts.
- **How long it remains valid:** 24 hours (stored in the `idempotency_keys` PostgreSQL table — no Redis required. See `06_Database_Design.md` Section 13).
- **Where it is stored:** Passed in the payload, checked against recent transactions for the same customer/business combo within a time window.
- **Duplicate request behaviour:** The server immediately returns `200 OK` with the existing transaction ID if the key was already successfully processed.
- **Retry behaviour:** Safely replays the request without creating a second record.
- **Network timeout behaviour:** The client can retry with the _same_ idempotency key.
- **Browser refresh behaviour:** A new page load generates a new idempotency key, but the UI state is reset, preventing accidental double-submits.
- **Server restart behaviour:** The atomic database transaction ensures no partial state exists.

**CRITICAL RULE:** A duplicate request must never create a second transaction.

# 32. Failure Recovery Matrix

| Failure                    | Rollback Required                          | User Experience                 | Recovery Action                               |
| -------------------------- | ------------------------------------------ | ------------------------------- | --------------------------------------------- |
| Wallet update failure      | Yes                                        | "Insufficient balance."         | User returns to Catalog/Reward screen.        |
| Ledger insert failure      | Yes                                        | "Unable to process rewards."    | User taps retry button.                       |
| Transaction insert failure | Yes                                        | "Transaction failed."           | User taps retry button.                       |
| Dashboard refresh failure  | No                                         | Visit completes normally.       | Data refreshes on next page load.             |
| Network timeout            | No (if DB committed) / Yes (if DB aborted) | "Connection timed out."         | Check Recent Transactions, retry if missing.  |
| Session expiry             | Yes (handled implicitly)                   | Redirected to Login.            | User logs in and restarts flow.               |
| Duplicate request          | No                                         | Instantly navigates to Success. | None required (Idempotency protects).         |
| OTP verification failure   | Yes (soft abort)                           | "Invalid OTP."                  | User enters correct OTP or cancels reward.    |
| Database timeout           | Yes                                        | "System busy. Please retry."    | User taps retry button.                       |
| Server crash               | Yes (transaction aborted)                  | "Unexpected error."             | User taps retry button after server recovers. |
